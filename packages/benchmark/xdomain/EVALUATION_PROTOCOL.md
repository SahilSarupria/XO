# Cross-domain evaluation protocol (candidate)

What the evidence in this folder does and does NOT show, and the steps that only people can complete.

## Current evidence (all produced by `run-baseline.mts`; candidate, not accepted baselines)
- 9 synthetic documents / 48 clauses, 9 prompts, 21 domain-identification items, layout variants (plain, table, two-column,
  scanned, DOCX), and stress PDFs (long two-column prose, wrapped table).
- One real policy (`e2e-evidence-real-policy.md`, regenerated by `e2e-evidence.mts`): compile-time readiness only.

## Why this is not yet independent evidence
1. **Single annotator.** The documents, the gold labels and the domain packs were written by the same author as the compiler
   changes. Metrics from them are sanity checks.
2. **Synthetic text** is cleaner than real documents.
3. **Small N** (48 clauses): report "defect observed / not observed", not rates.

## Steps that need people (the tooling for each is here)
1. **Second, blind annotation.** `python3 annotation_export.py` writes `annotation-sheet.csv` WITHOUT the first annotator's labels.
   Give it to someone who did not write the corpus, with the guidelines below.
2. **Agreement.** `python3 agreement.py <their.csv>` prints per-field agreement and Cohen's kappa and lists every disagreement.
   Target: kappa >= 0.8 on `type`, `modality`, `outcome` before any metric from this corpus is quoted externally. Disagreements are
   adjudicated by a person (never by a rule or by the compiler's own output); the two clauses already flagged `label_disputed` and
   the one corrected label are listed in `README.md` for that reviewer.
3. **Held-out documents.** Collect real documents from domains the packs and corpus do NOT cover (e.g. healthcare, public
   procurement, lease agreements, an unfamiliar-language policy). Freeze them BEFORE running the compiler on them, label them
   blind, then run. A domain-agnostic claim is only supportable if accuracy holds there and unknown-domain detection fires.
4. **Runtime execution.** For rules classified `deterministic` / `human_required`, execute them through a runtime host with
   registered authorization (the benchmark package's `vertical-fixtures` cases already do this for 7 real-pipeline cases) and compare
   with the document's own examples (e.g. Appendix A of the real policy).
5. **Baseline decisions** are governed separately: see `BASELINE_REFRESH_PROPOSAL.md`.

## Annotation guidelines (for the second annotator)
- `type`: rule (a condition leads to a decision or consequence), obligation, permission, prohibition, procedure (a step), definition,
  reference (a fact or finding with no normative force).
- `modality`: must / must_not / may / should / declarative (states a fact or consequence without a modal).
- `outcome`: approve, deny, requires_approval (someone must approve), escalate (EXPLICIT referral/escalation, not mere notification),
  none (no decision outcome stated).
- `conditions`: the number of independent conditions in the sentence's explicit condition clause (an enumerated list counts each item);
  `exceptions`: the number of exception clauses ("unless", "except"); `temporal`: true when a duration/deadline/date is involved.
- Label what the TEXT says, not what the organisation would probably do. If a sentence is ambiguous, write `ambiguous` in the cell.
