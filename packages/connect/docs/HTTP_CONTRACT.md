# Connect HTTP contract v1 (`apps/api`, additive)

Auth: `Authorization: Bearer <key>` like all non-exempt routes. The caller is `req.principal`; body fields naming an owner/principal are ignored. Routes exist only when the host passes `connect` to the server; otherwise they are 404.
Errors: `{"error":{"code","message","retryable"}}`. 400 invalid_request, 401 unauthenticated, 403 denied, 404 not_found, 409 conflict, 422 limit_exceeded, 503 unavailable (retryable), 500 internal.

## Wording constraints for Studio

- Never present cloud as a source; use `coming_soon`.
- "Read" means content was read and counted. `ReadReport.evidence` says whether it is now RETAINED as eligible evidence (`retained`, durable host) or not (`not_retained`). Neither claims knowledge exists: knowledge is derived from retained evidence at query time (C7.3).
- Disconnect / exclusion: "XO stops reading. What XO already learned is kept."
- `access_ended`: do not say expired or revoked.
- File names: preview shows names live; Connect stores the chosen keys (relative paths) locally, and EI evidence for local files includes names (observed in the demo). "XO keeps no file names" is false for local folders.

### D-1 design as built (no C4 change was needed)

Deletions can be detected statelessly if the connector is told which resources are in scope:

1. **C2 (additive):** `FilesystemScope.includeKeys?: string[]` (bounded, validated by the existing lexical key guard) and a real `incrementalSync` on `LocalFilesystemConnector`, implemented over the existing audited, authorized, fd-anchored acquisition path (permission `filesystem.read`). It returns evidence for present included files, `removed: [{resourceKey, reason: 'deleted'}]` for included keys that no longer exist, and a cursor that is a digest of the (key, content hash) manifest, so an unchanged tree yields no progress. Capped at the connector's per-call limit (200 items); more is refused with a clear error, never truncated.
2. Update the descriptor (`incremental_sync: 'supported'`, `requiredPermissions.incremental_sync`) and the conformance tests that pin it (`connector-registration`, `connector-audit-parity`, `connector-enforcement`).
3. **Host:** start `EiStateStore` (needs an audit-read grant and the ledger), run `ingestSource`, then `deriveKnowledge`. This also makes the inventory durable.
4. **D-3 then composes** `revokeSourceEvidence` + `purgeSourceEvidence` over a resource-to-evidence map built from `state.ingestedResources` and `resourceDigestOf(sourceId, kind, key)`, with dependency counts from provenance.

## C7.3 findings (verified, not assumed)

- **Chain proven through the real C6 SDK:** retained evidence is derived into the in-memory model and answers `query` with evidence references; deletion retires it; a principal without `data.read` on knowledge is denied by C6 itself; removal sweeps what was derived. Connect adds no retrieval, ranking, visibility or authorization of its own.
- **Free text does not become knowledge today, by design.** The filesystem connector keeps no file text (only a digest, byte length and strict-pattern business tokens such as `INV-1042`), and C5's shipped `StructuredRecordDeriver` understands only `ei.org-record.v1` records. Every read therefore reports `notUnderstood`, and the dashboard says "only structured organizational records become knowledge today". Wording must never imply that reading a document makes XO understand it.
- **Knowledge is memory-only.** After a restart the dashboard says `empty` until a source is read again, then the model is rebuilt from the durable index (no new ingestion needed). The staged payloads are re-read by acquisition.
- **Decision needed (product):** how local documents should become knowledge. Options: (a) the connector validates structured JSON record files and emits `ei.org-record.v1` evidence (deterministic, retains only validated fields); (b) a deriver over the identifier tokens (document-mentions-token facts, inferred and single-source); (c) an extraction model, which needs its own safety design. Until chosen, `createConnectRuntime` accepts an injected `deriver` and tests use a stand-in.

## Structured record files and per-item removal (built)

- **Record files become knowledge.** A chosen `.json` file shaped `{"schema":"ei.org-record.v1","records":[...]}` (at most 200 records, shallow, whole file read) carries its records in its content evidence (connector option `structuredRecords`, on whenever the host keeps knowledge). `FileRecordsDeriver` hands each record to C5's shipped `StructuredRecordDeriver`. Whole-file fail-safe: if any record is refused, the file contributes nothing and is counted in `notUnderstood`. A file whose facts exceed C5's per-evidence limit (64) is refused as `limit_exceeded`; split it. Free text and JSON that is not a record file keep only a digest, a length and strict business tokens.
- **Per-item removal** uses a new journal retire reason `removed`, a new audited EI operation `removeResourceEvidence` (needs `data.delete`) and a scope `epoch` so a removed item that is chosen again is read afresh instead of being skipped as "unchanged since the last checkpoint".
