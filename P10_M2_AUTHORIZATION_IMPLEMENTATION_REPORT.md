## 2. Findings and fixes

### Finding A — authorization before persistent execution-record creation

- **Root cause:** `executeApprovedCapability` created the execution record before authorizing.
- **Fix (already on the branch, re-verified):** `preflightCapabilityAuthorization` resolves the authoritative graph/capability/declaration and authorizes **before** `executionStore.create`. The route maps denial to HTTP 403. The execution boundary (`executeApprovedCapability` → `executeResolvedContract` → `RuntimeCapabilityExecutor`) re-derives the declaration from the same graph and authorizes again, so the preflight is never the only boundary.
- **Added this session:** a **declaration fingerprint** tie. The old TOCTOU tie used `graph.contentHash()`, which trusts stored node hashes and cannot see a property edit that leaves a node's hash unchanged. `preflightCapabilityAuthorization` now returns `declarationFingerprint` (canonical id + kind + sorted requirements); `executeApprovedCapability` derives the declaration once, compares it to the fingerprint, and uses that same declaration for the decision. Mismatch ⇒ `RUNTIME_PERMISSION_DENIED`, nothing executes.
- **Tests:** `apps/api/test/execution-preflight.test.ts` (12 tests, A1–A11). Denial ⇒ expected 403, store unchanged, handler/evaluator invoked 0 times; authorized path still executes once; direct runtime invocation without the route is denied; malformed/unresolved declarations fail closed. **A11** edits the declaration after the preflight (looser, different, stricter, removed) while asserting the graph content hash is unchanged (so the test proves the fingerprint, not the hash, catches it).
- **Negative control (run this session):** with the fingerprint check disabled A11 fails (11 pass / 1 fail); restored, 12/12 pass.
- **No new side effect:** denied attempts are not persisted or audited (durable audit belongs to M4).

### Finding B — forged permission declarations

- **Root cause (original):** the caller-supplied `permissionDeclaration` was accepted on structural similarity.
- **Previous fix:** declarations are minted per capability (`resolveAuthoritativeDeclaration` / `attestAuthoritativeDeclaration`, in-process `WeakMap` provenance + frozen result), verified by `isAuthoritativeDeclarationFor(declaration, capabilityId)`.
- **Gap found this session (the previous fix was only partial):** that verification ran only inside `executeResolvedContract`. The shared decision function `authorizeCapabilityExecution` accepted any `{ kind: 'none' }` literal, so every other consumer (executor, manifest gate, workflow runner, HITL resolver) trusted its declaration source without a runtime provenance check.
- **Fix:** `authorizeCapabilityExecution` now requires a declaration minted for **exactly** `requester.capabilityId`. `unresolved` declarations keep their own diagnostic reason; `none`/`required` must verify provenance or are denied. Consequently:
  - `RuntimeCapabilityRegistry.permissionDeclaration()` mints a fresh declaration per call (origin `trusted-host-registration`).
  - `createPermissionManagerGate` mints its manifest-composed declaration (origin `installed-package-manifest`).
  - CLI `deterministic-router` authorized under the manifest `capabilityId` while minting for `contract.id`; those can differ (`execution.contractId`). With central enforcement that would have denied legitimate execution (fail-closed, not a bypass). The requester identity is now `contract.id`, the same identity `executeResolvedContract` decides on. This does not weaken identity checks and does not touch M1 principal semantics.
- **`requiredPermissions: []` stays valid** when it is authoritative (minted); a forged empty declaration is denied.
- **Tests / negative controls:**
  - `packages/permissions/test/authorization.test.ts` (146 total): forged literal, frozen literal, shared `PERMISSION_FREE`, JSON clone, spread copy, `Object.create(minted)`, `structuredClone`, cast empty `required`, fewer-permission forgery, cross-capability replay, altered id (suffix/case), minted-but-unresolved, no-subject with minted declaration, bad mint inputs — all under an allow-everything policy so only provenance can deny. Without the fix, 3 of these fail; with it all pass.
  - `packages/runtime/test/capability-authority/authoritative-declaration.test.ts` (16): B1–B3 **tightened** (assert stage `authorization`, code `RUNTIME_PERMISSION_DENIED`, message "not resolved from an authoritative source", handler 0, **plus a positive control** with a minted declaration through the same call, so an unrelated earlier validation error cannot make them pass). **B14** registry mints per capability, copies/replays do not verify. **B15/B16** a tampered registry returning a forged literal / shared constant / JSON clone / a declaration minted for another capability is denied at the executor; handler never runs. Without the central fix B15 and B16 fail; with it they pass.
  - `apps/cli/test/authorization.test.ts` (11): new identity test — manifest id `claim_approval` with contract id `claim_contract` executes permission-free with no grant, is denied without a grant when a permission is declared, and is allowed with the grant. **Negative control:** with the router change reverted the test fails (10/1); restored, 11/11.
- **Test-file migration (disclosed, not a weakening):** the permissions tests that called `authorizeCapabilityExecution` with literal declarations now mint them (`mint(...)`), because literals are now correctly denied; assertions about permission matching are unchanged.

## 4. Threat model and trust-boundary limits

- **Defended:** a caller (HTTP client, CLI flags/input, persisted/serialized data, a different capability's declaration) cannot establish authorization by supplying an object that has the right shape. Provenance is a runtime property of the object (module-private `WeakMap` + frozen), bound to the exact capability id and checked at the single decision function every path funnels through. JSON/`structuredClone`/spread/prototype copies and casts do not carry it.
- **Not defended (stated plainly):** code already running **inside the same process** can import and call `attestAuthoritativeDeclaration` (or replace a registry method, as the B15/B16 tests do) and mint anything. This is an in-process provenance marker, not a sandbox. The registry is a trusted-host registration point: whoever registers a capability declares its permissions.
- **Default-deny unchanged:** no grant ⇒ denied; permission-free requires an authoritative empty declaration; missing/malformed/unresolved ⇒ denied.
- **Principal semantics (M1):** unchanged. A verified subject is still required (a minted permission-free declaration with no/unverified subject is denied — tested). Capability/package ids are never principals.

## 7. Intentional contract and behavior changes

- `POST /executions` for an unauthorized caller now returns **403** (previously a failed execution record could be created). No record is created on denial.
- Declarations that are not minted for the exact capability are denied at `authorizeCapabilityExecution` for every caller; test code that passed literals was migrated to mint.
- CLI deterministic router authorizes under `contract.id`.

## 8. Remaining risks / limitations

1. In-process provenance only (see §4); `attestAuthoritativeDeclaration` is a public export, and `allowAllPermissionGate` is a public explicit opt-out.
2. The registry's declaration for a workflow/CLI step comes from the contract copy at registration; for API workflow steps it is cross-checked against the persisted node (conflict ⇒ denied). The CLI workflow precheck is advisory; the executor decision is authoritative.
3. Denied attempts are not durably audited (M4).
4. PR comments and GitHub Actions for the candidate are unverified (see §1, §6).
5. Persisted graph node hashes are still trusted by `fromJson`; M2 no longer relies on them for authorization consistency (declaration fingerprint), but package/graph integrity is out of M2 scope (M5).
