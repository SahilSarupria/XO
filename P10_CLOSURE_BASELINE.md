## 5. R10 and R11: exact guarantees

### Crash states (what is possible, what covers it)

| State                                                          | What exists afterwards                                                     | Covered by                                                                                                               |
| -------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Crash before the precondition append                           | Nothing: no event, no side effect                                          | Fail-closed ordering (`audit.test.ts`, `audit-workflow.test.ts`)                                                         |
| Crash mid-append (torn tail)                                   | A partial line; no receipt was returned, so the guarded mutation never ran | `file-store.test.ts` torn tail, torn tail at open: terminated on next append, reported as `corruptLines`, never repaired |
| Crash after the precondition `fsync`, before the side effect   | Attempt event, no outcome, no side effect                                  | Indistinguishable from the next state by audit alone; cross-check the record                                             |
| **Crash after the side effect, before the completion append**  | Attempt event, a real execution/workflow record, **no outcome event**      | **New:** `audit-durable-e2e` #5 (real store) and `audit.test.ts` / `audit-workflow.test.ts` (sink port)                  |
| Append written but acknowledgement lost (fsync failure, crash) | The line may or may not exist; the caller has no receipt (indeterminate)   | `file-store.test.ts` fsync failure; retry with an `idempotencyKey` never duplicates                                      |
| Crash during purge                                             | The original file, intact (temp + fsync + rename)                          | `file-store.test.ts` crash during purge                                                                                  |
| Crash holding the writer lock                                  | A stale lock, stolen after 30 s                                            | `file-store.test.ts` stale lock                                                                                          |
| Power loss / media failure                                     | Whatever the OS and disk honour for `fsync`                                | **Not guaranteed, not tested**                                                                                           |

The crash window is **detectable, not solved**: the documented procedure (find `*.started`/`*.attempted` with no later outcome for a correlation id, cross-check against the record, never re-run) is manual and has no tool. Closing it fully (an outbox or a recovery job) is a design change and is not part of this closure.

### Filesystem, process and locking boundary (R11)

- One process owns a directory: strong guarantees (fsync receipts, gap-free `seq`).
- Several processes on one **local POSIX** filesystem are coordinated by an advisory lock file with stale-lock stealing; tested for two store instances.
- Not guaranteed: network filesystems, multi-host, replication, distributed ordering. Nothing here may be described as distributed or multi-host safe.
- The API's idempotency coordination is in-process (M6). D1 (single-tenant, one deployment) is the approved deployment model.
