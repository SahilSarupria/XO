## 7. Observations and limitations (not settled here)

1. **Confidence gate is not applied on the API path (OBSERVED).** `RuntimeCapabilityExecutor` enforces a floor only when the caller passes `minConfidence`; `executeApprovedCapability` passes none, and no code in `apps/api/src` passes `minConfidence` or `confidenceScore`. The approval digest deliberately excludes confidence. This predates M6 and affects every API execution route. M3 requirement text is UNAVAILABLE, so I cannot say whether M3 required it. **Owner decision:** is a host-configured floor wanted for procedure steps? Not changed.
2. **A later execution blocked by an earlier unknown outcome is reported by MCP as a plain `failed` (OBSERVED).** The API maps `blocked_prior_dispatch` to "not dispatched" (correct for that attempt); the adapter keys "unknown" only on `XO_EXTERNAL_EFFECT_OUTCOME_UNKNOWN`. Nothing unsafe: no dispatch occurs. A reconciliation-required hint in the MCP result is a possible owner-requested improvement.
3. **Client retry / idempotency policy unchanged (M5 §9-5).** The idempotency key is per JSON-RPC request id. By code reading, a client retry after a lost response to a call that had **completed** starts a new execution and may legitimately repeat the effect; a retry after an **unknown** outcome is blocked by the M4 ledger. Not re-demonstrated by a test here (the adapter e2e that covers the second case is SDK-backed).
4. **Audit attribution unchanged (M5 §7/§9-4):** MCP-originated starts are indistinguishable from other API calls by the same principal.
5. M4's own recorded limits stand: single-filesystem atomicity, one host clock for freshness, ledger/audit not atomic, retention report-only, no shipped entrypoint enables adapters, in-memory ledger only under explicit test opt-in.
6. M3 known limitations stand (timeout does not cancel in-flight work, in-process locking, best-effort detail audit, simulated crash-at-write).
7. No `tsconfig` for `apps/api`, `apps/mcp` or the M1–M5 packages includes test files (only `atlas` and `marketplace-world` have a `tsconfig.test.json`), so `tsc -b` does not typecheck these tests. An ad hoc typecheck of the new file reports one diagnostic, the `workspaceCompilationsStore(..., { dataRootDir })` call pattern that existing tests (`e2e-api`, `workflow-fixtures.ts`) share.
