# P1.0 — Enterprise Trust: Decision Record

Authoritative record. Status of each entry is stated explicitly. This file does not create a roadmap phase and does not modify the frozen master roadmap (P0.9A/B/C closed → P1.0 → P1.1 → P1.2 → Multi-XO foundation → P1.5 → P1.7 → P2 → P3).

## A. APPROVED decisions (by the user; D1–D3 recorded at P1.0 M1 start, D4 at M5)

| #   | Decision                                                                                                                                                                                                                                         | Status   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| D1  | **Deployment model:** single-tenant, one business per deployment initially. Workspace isolation is preserved. Interfaces stay extensible for future multi-organization deployments.                                                              | APPROVED |
| D2  | **Principal model:** minimal authenticated human / service principal with a stable id and optional `orgId`. Package and capability identities remain separate from the initiating principal.                                                     | APPROVED |
| D3  | **AI execution exposure:** AI execution remains disabled until its path enforces effective authorization. It is not re-enabled by M1.                                                                                                            | APPROVED |
| D4  | **Package trust default (M5, approved 2026-10-13):** an explicit development compatibility mode is approved; production and enterprise package operations REQUIRE a configured trust policy. A missing policy is never read as development mode. | APPROVED |

## C. Explicitly NOT decided here

Role/permission model, org membership, SSO/IdP, key rotation/expiry/scopes, authorization gate semantics (M2), approval binding (M3), audit ledger (M4), package trust beyond the default-policy decision D4 (M5 — key custody, certificate chains and multi-signature approval remain undecided), idempotency (M6), endpoint hardening (M7).

## D. Proposed for review (NOT implemented, NOT approved)

**Key-migration helper.** An operator command such as `manage-keys.ts bind <identityId> --kind human|service [--org <orgId>]` that attaches a principal binding to an _existing_ unbound key record so callers need not receive new keys. Open questions for review: (a) it asserts a kind for a credential whose holder the tool cannot verify (the operator is vouching); (b) it should require an explicit per-identity confirmation and refuse to touch revoked keys; (c) whether re-issuing (current documented path) is preferable because it forces key rotation. Until approved, the only supported path is revoke-then-reissue with an explicit `--kind`.

## G. M5 package trust — implementation details established by inspecting the repository (NOT user decisions)

Chosen by the implementer; reviewable and reversible. No frozen M5 specification existed in the repository, so everything below is a proposal built on the scope in the M5 brief. They do not reopen A–F.

| #   | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Basis                                                                                                                                                                                                                                                                      |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M5a | Trust anchors are an operator-controlled policy file (`XO_PACKAGE_TRUST_POLICY`, JSON v1): Ed25519 keys bound to a signer DID, status `active`/`revoked`, optional validity window. Nothing carried by a package or request (a `publicKeyPem` beside a signature, API `publicKeys`) is ever consulted.                                                                                                                                                           | Brief §4A. Existing code let the caller/package supply the key (`/packages/validate` `publicKeys`, `SignatureEntry.publicKeyPem`).                                                                                                                                         |
| M5b | ~~**Default is unenforced.**~~ **SUPERSEDED by D4 (2026-10-13).** Original text: with no policy configured nothing was verified, no package was reported `trusted`, and the API logged a startup warning; a configured-but-broken policy aborted startup. That permissive default is removed — see M5g–M5l. The configured-but-broken half is retained and strengthened.                                                                                         | Original basis: locally compiled packages are unsigned and default-deny would stop every compile→install→run flow. The owner decided that cost is accepted for production/enterprise and is carried by an explicit development mode instead (D4).                          |
| M5c | Under an enforcing policy: a signature is required (default), the `creator` role is required (default), the creator signer must equal `manifest.creatorDid` (publisher binding), and EVERY signature entry must verify (malformed, unknown-signer, revoked, out-of-window or non-verifying entries fail the package).                                                                                                                                            | Fail-closed on unknown/untrusted identities.                                                                                                                                                                                                                               |
| M5d | Revocation is conservative: a signature by a now-revoked key is rejected regardless of when it was made (the format has no trustworthy signing time). Rotation = add the new key, revoke the old one, re-sign.                                                                                                                                                                                                                                                   | Brief §4C: do not fabricate lifecycle support.                                                                                                                                                                                                                             |
| M5e | No format change. The signed bytes are unchanged (`signableManifestBytes`). The install record gains optional `manifestDigest` (full manifest incl. signatures) and `trust`; pre-M5 records stay readable.                                                                                                                                                                                                                                                       | Brief §4B.                                                                                                                                                                                                                                                                 |
| M5f | Mount re-evaluates trust under the _current_ policy from a single read (`PackageInstaller.loadVerified`); component reads re-check the manifest hash.                                                                                                                                                                                                                                                                                                            | Brief §4E (no check-then-reread).                                                                                                                                                                                                                                          |
| M5g | **Trust mode is explicit and fail-closed.** Two modes only: `enforce` (default when `XO_TRUST_MODE` is unset) and `development` (only when `XO_TRUST_MODE=development`). With `enforce` and no `XO_PACKAGE_TRUST_POLICY`, every protected operation fails with `XO_PACKAGE_TRUST_NOT_CONFIGURED`. The former `unenforced` policy/status/constructor no longer exists.                                                                                            | D4. Resolution table in `docs/package-trust-operations.md`.                                                                                                                                                                                                                |
| M5h | **Development mode cannot be enabled by accident.** It is refused when `NODE_ENV=production` (environment or injected policy — `assertTrustPolicyAllowedHere` is applied by the resolver, the API and the CLI), refused when combined with a policy file, unreachable from policy data (a file's `mode` may only be `enforce`), and unknown/near-miss spellings (`dev`, `Development`, `true`, `off`, …) are errors.                                             | D4 / requirement 7.                                                                                                                                                                                                                                                        |
| M5i | **Development mode is never "trusted".** Verdict status `unverified`, mode `development`; install records carry `trust.mode`; surfaced at API startup, in `bootstrapWarnings`, in `/packages/validate` and registry-publish `trust` objects, in validation reports (`TRUST_DEVELOPMENT_MODE`), on every CLI install/verify/publish/run, and in `xo doctor`.                                                                                                      | D4 / requirement 4.                                                                                                                                                                                                                                                        |
| M5j | **One resolver for every entry point.** `loadOperatorTrustPolicy` is the sole source of the effective policy for CLI install/verify/publish/run, API startup (validate, registry publish, runtime bootstrap/mount) and `xo doctor`. `PackageValidator`/`PackageInstaller`/`RegistryClient` built with no policy are _unconfigured_ and fail closed (`TRUST_NOT_CONFIGURED`, `XO_PACKAGE_TRUST_NOT_CONFIGURED` at install); `skipValidation` never bypasses this. | Requirement 5.                                                                                                                                                                                                                                                             |
| M5k | **`resolvePublicKey` and `xo verify --pubkey` are development-only.** They require an explicit development policy and are refused under an enforcing one, so neither can produce a "valid" the policy would reject.                                                                                                                                                                                                                                              | Closes a bypass found while inspecting entry points: the legacy resolver could previously stand beside, or in place of, a policy.                                                                                                                                          |
| M5l | **Authoring commands (`create`, `build`, `pack`) use an explicit development-mode structural validator** (`authoringValidator()`). They admit/publish/mount/run nothing, so no policy applies, and they never claim trust; their throw-away dev-key signatures are not trusted by any enforcing policy.                                                                                                                                                          | Inspected: they call `validateAll` but write only a file. Requiring a policy would break authoring in production-configured environments without protecting anything. Reviewable: if the owner wants authoring gated too, it is a one-line change in `authoringValidator`. |
